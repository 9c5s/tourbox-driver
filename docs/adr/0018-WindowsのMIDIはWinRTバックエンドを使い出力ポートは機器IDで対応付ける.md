# ADR-0018: Windows の MIDI は WinRT バックエンドを使い、出力ポートは機器 ID で対応付ける

- 状態: 承認 (2026-09-24、Discord で承認)
- 日付: 2026-09-24

## 文脈

設計書 6.1 節と 6.2 節は、Windows では既存の MIDI ポートを名前で選び、接続中も 5 秒ごとに一覧を再評価してポートの消失と再出現を検知すると定めている。
midir の Windows 既定バックエンドは WinMM (従来の MME API) である。
2026-09-24 の受け入れ確認 5 (loopMIDI を終了して 12 秒後に再起動) で、次の事実を実機 (Windows 10) で確認した。

- 起動中のプロセスでは WinMM のポート一覧が更新されない。loopMIDI を終了しても常駐アプリの一覧には残り、新しいプロセスから見ると消えている。メッセージポンプを動かしても変わらない。
- 再起動後、古い接続への送信は成功として扱われるが新しいポートには届かず、入力も受信しない。
- 設定ファイルの保存し直しで入力ポートを開き直しても、古い一覧に基づく open は成功するが受信しない。つまり設計書 6.2 節の復旧手順は成立せず、アプリの再起動でしか復帰できない。

midir の WinRT バックエンド (`winrt` feature。Windows 10 以降の Windows.Devices.Midi) を同じ条件で検証した。

- ポートの消失と再出現は 2 秒以内に一覧へ反映される。
- loopMIDI のポートに対する送受信は双方向とも動作する。
- 入力ポートの名前は「TourBox MIDI Out [1]」のように末尾に番号が付く。出力ポートの名前は loopMIDI では「MIDI」としか得られず、名前では選べない。ただし機器 ID (`\\?\SWD#MMDEVAPI#MIDII_F20B738C.P_0000#{...}`) の `MIDII_` に続く機器の識別子は、同じ loopMIDI ポートの入力と出力で一致する。

## 決定

Windows では midir の `winrt` feature を有効にし、WinMM を使わない。
ポートの選択は、まず名前 (完全一致、なければ部分一致) で行う。
出力ポートが名前で見つからない場合は、名前が一致する入力ポートを探し、その機器 ID の識別子 (`MIDII_` に続く部分) が一致する出力ポートを選ぶ。
`list-ports` は Windows で名前に加えて機器 ID の識別子を表示し、出力名が「MIDI」でも対応が分かるようにする。
5 秒ごとの一覧再評価と、設定の保存し直しによる開き直しは、設計書どおりの動作に戻る。
対象は Windows 10 (バージョン 1809) 以降とし、README に書く。

## 検討した選択肢

- WinMM のまま、ポートの増減を別プロセス (`list-ports` 相当) で検知し、押下中の Note を解放してから自プロセスを再起動する。実装は単純だが、再起動のたびに絶対 CC の内部値が失われ、常駐アプリが自分を再起動する挙動は利用者に分かりにくい。
- MIDI の入出力を補助プロセスに分け、増減のたびに補助プロセスだけを再起動する。プロセス間通信が増え、今回の要件には過剰である。
- Windows MIDI Services を使う。Windows 11 限定で、対象 OS の Windows 10 で使えない。
- 既知の制限として README に「loopMIDI を再起動したらアプリも再起動する」と書くだけにする。設計書 6.1 節の自動復帰の要件を満たさない。

## 結果

- `crates/tourbox-midi/Cargo.toml` の midir に `cfg(windows)` で `winrt` feature を付ける。macOS は CoreMIDI のまま変わらない。
- Windows のポート名は WinMM と異なる (入力名の末尾の番号、出力名の欠落)。設定の `output` と `input` は部分一致で選ぶため、loopMIDI のポート名をそのまま書けば従来どおり動く。
- 受け入れ確認 5 と 5b を WinRT で再実施する。5b (5 秒未満の再起動) は、一覧の再評価が生きているため検知できる見込みだが、実機で確認する。
- 設計書 6.1 節と 6.2 節に WinRT の採用と出力ポートの対応付けを追記し、6.2 節の「5 秒未満の再起動」の制限は実機の結果で見直す。
