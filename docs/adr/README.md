# アーキテクチャ決定記録 (ADR)

このディレクトリには、TourBox Elite MIDI ドライバの設計上の決定を 1 件 1 ファイルで記録する。
設計仕様 (`docs/spec/`) は「いま何を作るか」を、ADR は「なぜそう決めたか」を持つ。

## 書き方

- ファイル名は `NNNN-題名.md` である。`NNNN` は 4 桁の連番で再利用しない。題名は本文の題名から空白と読点を除いた日本語で書く。
- 各 ADR は、題名、状態、日付、文脈、決定、検討した選択肢、結果の順で書く。
- 状態は「提案」「承認」「廃止」「置換 (ADR-NNNN による)」のいずれかである。
- 承認した ADR の決定は書き換えない。決定を変えるときは新しい ADR を書き、古い ADR の状態を「置換」にして相互に参照する。
- 文脈には、決定の時点で分かっていた事実と制約だけを書く。後から分かった事実は新しい ADR に書く。
- 1 件は 1 画面から 2 画面に収める。1 件には 1 つの決定だけを書く。
- 文体は常体 (である調) で書く。
- 形式は `cargo lint-adr` (`xtask/src/adr.rs`) で検査する。コミット時のフックと CI でも実行する。

## 書く基準

次のいずれかに当たる判断は、指示を待たずに ADR を書く (ADR-0014)。迷ったら書く。

- 依存クレートや外部ツールの選定と入れ替え
- 公開インターフェース (ライブラリの API、設定ファイルの構造、CLI) の追加と変更
- データ形式とプロトコルの解釈
- 運用と開発の手順 (ブランチ、レビュー、テスト、リリース)
- 対象範囲の変更
- 既存の ADR と矛盾する実装

判断が生じたら実装を止め、状態を「提案」にして書き、承認を得てから実装する。
承認済みの決定を変えるときは新しい ADR で置換する。
後から分かった事実は、関係する ADR の結果に日付付きで追記する。
