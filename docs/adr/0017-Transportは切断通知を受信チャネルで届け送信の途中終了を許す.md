# ADR-0017: Transport は切断通知を受信チャネルで届け、送信の途中終了を許す

- 状態: 承認 (2026-09-23、Discord で承認)
- 日付: 2026-09-23

## 文脈

設計書 4.2 節は `Transport` トレイトの提供物を「送信、受信チャネル、切断通知、停止」の 4 つと定めるが、その形と契約の細部は決めていない。
実装計画 Task 4 (2026-09-23) は、受信と切断通知を 1 本の `tokio::sync::mpsc` チャネルの列挙型 (`Incoming::Data(Vec<u8>)` と `Incoming::Disconnected`) で順序どおり届け、チャネルは接続ごとに 1 回だけ取り出す形で実装した。
非同期メソッドは `futures::future::BoxFuture` を返し、`Box<dyn Transport>` として扱える。
Task 4 のレビューで、次の 2 点が未規定と指摘された。

- `send` と `close` はどちらも `&mut self` を取るため、送信中に停止要求が来た場合、device は送信の完了を待つか、`send` の future を破棄するかのどちらかしかできない。BLE の書き込みが停滞すると、完了待ちは停止 (`shutdown`) を止める。
- `Incoming::Disconnected` が届かずにチャネルが閉じた場合 (実装の異常終了など) を device が切断として扱うべきかが書かれていない。

## 決定

- 受信と切断通知は 1 本のチャネルで届ける。`Disconnected` は切断時の最後の要素で、その後チャネルは閉じる。`close` による終了では `Disconnected` を送らない。
- `send` の future は途中で破棄してよい。破棄した送信が行われたかどうかは不定とし、破棄の後も `close` は正常に動く。device の `shutdown` は進行中の送信を待たずに破棄して `close` を呼ぶ。
- device は、`Disconnected` を受け取った場合に加えて、`Disconnected` なしで受信チャネルが閉じた場合も切断として扱う。実装 (usb、ble) は `close` 以外の終了で必ず `Disconnected` を送る。
- これらの契約は `Transport` の doc コメントに書く。

## 検討した選択肢

- 切断通知を別のチャネルや `oneshot` で届ける。受信データと切断の順序が保てず、device の待ち受けが複雑になる。
- 送信の完了を待ってから `close` する。停滞した書き込みで `shutdown` が戻らなくなる。
- `send` を `&self` にして `close` と同時に呼べるようにする。実装の内部で排他が必要になり、フェイクとテストも複雑になる。

## 結果

- Task 5 の device は停止要求と送信を `select!` で待ち受け、停止要求が勝ったら送信を破棄する。
- USB 実装 (Task 6) では、破棄しても専用スレッドの書き込みは止まらない。`close` はスレッドの終了を待つので、書き込みが完了してから戻る。
- フェイク (Task 4) は破棄した送信を記録しない。この振る舞いは本 ADR の「不定」の一例である。
- 2026-09-23: BLE 実装 (Task 7) では、送信の future を破棄すると残りの 20 バイト分割を送らない。macOS ではキューに積まれた分割が後から送られることもある。どちらも「不定」の範囲内である。
