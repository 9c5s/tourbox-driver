# ADR-0003: 通信ライブラリと MIDI アプリの 2 クレートに分ける

- 状態: 承認 (2026-09-23、Discord で承認)
- 日付: 2026-09-23

## 文脈

出力を MIDI に限定した (ADR-0001) が、デバイス通信 (USB、BLE、初期化、イベント復号、ハプティクス設定) と MIDI 変換 (設定ファイル、修飾レイヤ、ポート選択) は関心が異なる。
通信部分は実機がないとテストしにくく、変換部分は実機なしで表駆動テストできる。

## 決定

Cargo ワークスペースに 2 つのクレートを置く。
`tourbox` (ライブラリ) は protocol、transport、device を持ち、MIDI を一切知らない。
`tourbox-midi` (実行ファイル) は config、engine、midi、haptics、commands を持ち、プロトコルのバイト列を一切知らない。
transport はトレイトで抽象化し、テスト用のフェイクを `fake` feature で公開する。

## 検討した選択肢

- 単一クレート。最も速く動くが、通信と変換が混ざってテストと再利用が難しくなり、「ライブラリを土台にする」方針と合わない。
- デーモンと IPC (コアが常駐して WebSocket などでイベントを配信し、MIDI 変換は別クライアント)。他言語のクライアントを足しやすいが、プロセス間通信の設計、起動順序、エラー伝播が増え、今回の要件には過剰である。

## 結果

- ライブラリは実機なしで単体テストでき、将来別の出力を作るときもライブラリを変更せずに済む。
- 実行ファイルは lib と薄い main の 2 ターゲットにし、テストが内部 API に届くようにする (Codex レビュー round 1 の指摘による)。
- 別言語からライブラリを使うには、後で FFI か IPC を足す必要がある。
