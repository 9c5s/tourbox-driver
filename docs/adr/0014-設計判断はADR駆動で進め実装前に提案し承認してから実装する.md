# ADR-0014: 設計判断は ADR 駆動で進め、実装前に提案し承認してから実装する

- 状態: 承認 (2026-09-23、Discord で承認)
- 日付: 2026-09-23

## 文脈

ADR-0000 で設計上の決定を ADR に記録すると決め、ADR-0001 から ADR-0013 は設計セッションの対話を後からまとめる形で書いた。
文体の規則 (ADR-0013) はユーザーに「これ自体も ADR ではないか」と指摘されて書いており、何を ADR にするかの判断が担当側に委ねられていなかった。
ユーザーは「ADR に書くべきものは自分で判断して自分で書く」「作業フローも ADR 駆動開発のベストプラクティスに従う」と指示した。
実装は次のセッションからサブエージェント駆動で進める (ADR-0010)。実装中には、クレートの選定や公開インターフェースの変更のような判断が発生する。

## 決定

設計判断は ADR 駆動で進める。

1. **書く基準を担当側が持つ。** 次のいずれかに当たる判断は、指示を待たずに ADR を書く。依存クレートや外部ツールの選定と入れ替え、公開インターフェース (ライブラリの API、設定ファイルの構造、CLI) の追加と変更、データ形式とプロトコルの解釈、運用と開発の手順 (ブランチ、レビュー、テスト、リリース)、対象範囲の変更、既存 ADR と矛盾する実装。迷ったら書く。
2. **実装の前に書く。** 判断が生じたら実装を止め、状態を「提案」にした ADR を書いてユーザーの承認を求める。承認で「承認」に変えてから実装する。実装計画の各タスクでこの判断が出た場合、サブエージェントは実装を続けずに統括側へ報告し、統括側が ADR を書く。
3. **承認済みの決定は書き換えない。** 変えるときは新しい ADR で置換する (ADR-0000 の規約)。実装や実機で後から分かった事実は、関係する ADR の結果に日付付きで追記する。
4. **変更と同じコミットに入れる。** ADR は、その決定を実装するコミットか、実装より前の独立したコミットに含める。コミット時と CI の形式検査 (ADR-0012) で規約を保つ。
5. **一覧を入口にする。** `docs/adr/README.md` の一覧を最新に保ち、設計書と実装計画は決定の理由を ADR 番号で参照する。

## 検討した選択肢

- 指示があったときだけ ADR を書く。判断の記録が抜け、後から理由を再構成することになる。
- 実装後にまとめて ADR を書く。実装と判断がずれたときに手戻りが大きく、承認を得ずに進めた判断が残る。
- 設計書に判断を追記する。ADR-0000 で退けた案であり、変更履歴が追えない。

## 結果

- `docs/adr/README.md` に「書く基準」の節を置き、担当側が参照できるようにする。
- 実装計画の共通制約に「ADR に当たる判断が出たら実装を止めて ADR を書く」を加え、サブエージェントへの指示に含める。
- 「提案」の ADR が存在する間は、その決定に依存する実装を進めない。
