# ADR-0010: 実装は軽量な計画とサブエージェント駆動の TDD で進める

- 状態: 承認 (2026-09-23、Discord で承認)
- 日付: 2026-09-23

## 文脈

設計仕様は Codex のレビュー 6 round を経て、モジュール構成、契約、テスト項目、受け入れ確認まで書かれている。
superpowers の writing-plans は、各ステップにコードを書く完全な計画書を作る形式が既定である。
ユーザーは「実装計画には具体的なコードを含めず軽量にする」「実装は次のセッションで行う」「サブエージェント駆動 (SDD) のサブエージェントは Opus 5.5 を指定する」と指示した。
設計を行ったセッションは長く、要件確認、実機調査、レビューループを含んで文脈が重い。

## 決定

コードを含まない軽量な実装計画を 1 本書く (`docs/plan/2026-09-23-tourbox-midi-driver.md`、14 タスク)。
各タスクは、対象ファイル、他タスクとの受け渡し (型と関数の名前)、テストを先に書く手順、検証方法、コミットメッセージを箇条書きで示し、仕様の詳細は設計書を参照する。
実装は次のセッションで superpowers:subagent-driven-development により行い、タスクごとにフレッシュなサブエージェント (model は opus) が TDD で実装し、別のレビュー担当が確認してから次に進む。
実装計画も設計仕様と同じ Codex レビューループを通す。

## 検討した選択肢

- writing-plans の完全な計画書。ファイル構成とインターフェースを先に固定できるが、各ステップにコードを書くため実装を 2 回書くことになり、クレートの細部は実装しながら判明するため先行して書いたコードが古くなりやすい。
- 設計仕様だけを見て直接実装する。速いが、チェックリストがないと仕様からの漏れに気づきにくく、長いセッションでの直接実装は品質が下がる。
- ネイティブ (統括側のセッションで全タスクを順に実装し、最後に 1 回レビュー)。安く速いが、14 タスクが型や関数名の受け渡しで連鎖しており、通信層の間違いは実機でしか分からないため、タスクごとの独立レビューで受け渡しのずれを早く見つける方を優先した。

## 結果

- 計画のコストを抑えつつ、フレッシュな文脈での実装と、中断からの再開のしやすさを得る。
- 計画の各タスクは実機確認の手順を含み、実施できない場合は「未実施」と理由を記録する。
