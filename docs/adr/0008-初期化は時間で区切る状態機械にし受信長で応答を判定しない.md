# ADR-0008: 初期化は時間で区切る状態機械にし、受信長で応答を判定しない

- 状態: 承認 (2026-09-23)
- 日付: 2026-09-23

## 文脈

TourBox Elite はアンロックの 8 バイトを送ると 26 バイト程度の応答を返し、その後にハプティクス設定の 94 バイトを送るとイベントを 1 バイトずつ送り始める。
応答の末尾には `00` が続くため、これをイベントとして復号すると Tall の押下と誤認され、修飾が押しっぱなしになる。
tuxbox は「一度に 20 バイト以上まとまって届いた受信は応答フレームとみなして捨てる」方式で対処しており、当初の設計もこれを踏襲した。
Codex のレビューで、シリアルの読み取り境界はメッセージ境界と一致しないため、正常なイベントが 20 バイト以上まとまると全件捨てられ、分割された応答は判定を通過することが指摘された。
応答の先頭バイトはファームウェアにより異なり、応答完了を判定できるプロトコル上の条件は分かっていない。

## 決定

受信長で応答を判定しない。
初期化を `Unlocking`、`Configuring`、`Running` の状態機械にし、`Unlocking` と `Configuring` の受信はすべて捨てる。
`Unlocking` は最初の受信から 200 ms の静穏 (受信のたびに再設定) か、送信から 1 秒の打ち切りで抜ける。
`Configuring` は 94 バイトの送信完了から 200 ms 待つ。
`Running` では全バイトをイベントとして復号する。
アンロック前の書き込みに対する応答文字列 `<!not_allow_config!>` は、受信のかたまりをまたいで逐次照合する検出器で見つけ、再初期化する。

## 検討した選択肢

- 受信長 (20 バイト以上) で応答を判定する。上記のとおり誤判定の両方向があるため採らない。
- 応答を 26 バイト受け取った時点で次へ進む。ファームウェアで長さが異なる可能性があり、応答が来ない場合の扱いも要るため、静穏期間の補助にとどめる案として見送った。

## 結果

- 時間による区切りは保証ではない。応答の末尾が `Running` への移行後に届けば誤認は起きる。200 ms と 1 秒は実測のない初期値で、`dump` が各状態の受信時刻をログに出し、受け入れ確認で実機の遅延が収まることを確かめる (設計書 4.3 節、9 章)。
- `Running` 中に 20 バイト以上のイベントがまとまって届いても全件復号される。
