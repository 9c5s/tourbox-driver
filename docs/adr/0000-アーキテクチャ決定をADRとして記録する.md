# ADR-0000: アーキテクチャ決定を ADR として記録する

- 状態: 承認 (2026-09-23、Discord で承認)
- 日付: 2026-09-23

## 文脈

設計仕様 (`docs/spec/2026-09-23-tourbox-midi-driver-design.md`) と実装計画 (`docs/plan/2026-09-23-tourbox-midi-driver.md`) は、要件の対話と Codex のレビュー 6 round を経て書かれた。
その過程で、出力を MIDI に限定する、言語に Rust を選ぶ、仮想 MIDI ポートに loopMIDI を併用するといった判断を下し、却下した案もあった。
判断の理由と経緯は対話と Discord のやり取りにしか残っておらず、仕様書には決定の内容だけが書かれている。
ユーザーは別プロジェクト (cgss-emusrv) と同じ形式で ADR を残すよう指示した。

## 決定

設計上の決定は `docs/adr/` に、Michael Nygard の形式 (文脈、決定、結果) に「検討した選択肢」を加えた構成で、1 件 1 ファイルで記録する。
書き方の規約は `docs/adr/README.md` に置く。
設計仕様には決定の内容だけを書き、理由と経緯は ADR を参照する。
設計仕様は `docs/spec/`、実装計画は `docs/plan/`、プロトコルの採取資料は `docs/protocol/` に置き、ADR と同じくコミットする。

## 検討した選択肢

- 仕様書に理由と却下案を書き足す。仕様が長くなり、決定の変更履歴も追いにくいため採らない。
- コミットメッセージと PR の説明だけに理由を残す。設計判断はコードより前に下されており、対応するコミットがないため採らない。

## 結果

- 仕様書は設計の記述に集中できる。
- 決定を変えるときは新しい ADR を書き、古い ADR を「置換」にする。判断の変遷が番号順に追える。
- 形式の自動検査は行っていない。必要になったら実装計画の CI に追加する。
- 2026-09-23: 形式の自動検査を `cargo lint-adr` として追加した (ADR-0012)。上の 1 行は同 ADR で置き換える。
