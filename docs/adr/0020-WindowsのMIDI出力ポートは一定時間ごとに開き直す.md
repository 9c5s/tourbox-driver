# ADR-0020: Windows の MIDI 出力ポートは一定時間ごとに開き直す

- 状態: 承認 (2026-09-25、Discord で承認)
- 日付: 2026-09-24

## 文脈

ADR-0018 で Windows の MIDI は midir の WinRT バックエンドに切り替えた。
2026-09-24 の常駐試験で、19:21 (UTC) に開いた出力ポートへの最初の送信 (約 6.8 時間後) が、送信は成功として扱われるのに受信側へ届かない事象が起きた。
同じプロセスの入力ポートは受信を続けていた。
ポートの消失、loopMIDI の再起動、スリープはいずれも記録になく、常駐アプリを起動し直すと出力は復帰した。

原因を切り分けるため、使い捨てのプログラムで次を確認した (受信側は WinMM の別プロセスで、実験の間ずっと受信できていた)。

- 出力ポートを開いて 1 分、10 分、30 分、60 分、120 分待ってから 1 件送る (5 本の別プロセス): すべて届いた。
- 出力ポートを開いたまま、常駐アプリと同じく 5 秒ごとに WinRT でポートを列挙し、30 分ごとに 1 件送る: 30 分、60 分、90 分、120 分の送信は届き、150 分以降の 4 件は届かなかった。送信はエラーを返さない。

したがって、WinRT の出力ポートの接続は、開いてから約 2 時間を過ぎるとエラーなしに無効になる。
入力ポートには同じ現象が見られない。
5 秒ごとの一覧再評価はポートの消失を見るだけで、この無効化は検知できない。

## 決定

Windows の `Existing` モードの出力ポートは、開いてから 60 分が経過したら、次の 5 秒ごとの再評価の時点で閉じて開き直す。
開き直しの間は数十ミリ秒の送信不能があるが、台帳 (押下中の Note) は保持し、開き直しの直後に台帳の Off は送らない (接続が切れたわけではないため)。
開き直しに失敗した場合は通常の未接続として 5 秒ごとに再試行する。
開き直しは info ログに出す。
macOS の仮想ポートと入力ポートには適用しない。
60 分は、2 時間で無効化が起きた実測に対する余裕をとった値である。

## 検討した選択肢

- 送信のたびに開き直す。送信ごとに WinRT の接続を作り直すため遅延が大きく、連続する回転操作に向かない。
- 定期的に無害なメッセージ (Active Sensing) を送って接続を保つ。30 分ごとの送信でも無効化が起きており、効果が確認できない。受信側にも余分なメッセージが届く。
- 一定時間送信がなければ開き直す。無効化は送信の有無ではなく開いてからの時間で起きているので、条件が合わない。
- 原因を midir か Windows 側で突き止めて直す。送信がエラーを返さないため、アプリ側から検知する手段がなく、時間がかかる。

## 結果

- `OutputState` は開いた時刻を持ち、`tick()` で経過時間を見る。テストは時刻を注入して 60 分の境界を確かめる。
- 開き直しの間隔は設定にせず定数にする。実機で 60 分でも無効化が起きた場合はこの ADR を見直す。
- 無効化の境界 (2 時間から 2 時間半の間) と、待機だけで開き直さない場合の再現は、追加の実験で確かめる。
- 2026-09-25: 追加の実験で次が分かった。10 分ごとに送る接続は 7.7 時間 (46 回) すべて届いた。30 分ごとに送る接続は 2 回とも、開いてから 120 分までは届き、150 分から 240 分は届かず、270 分から 360 分は再び届き、390 分以降は届かなかった (2 時間ごとに届く期間と届かない期間が交互に現れる)。150 分待機してから 1 回だけ送る接続は届いた。したがって無効化は恒久ではなく、開いてからの時間だけでは決まらない。60 分ごとの開き直しの効果と、5 分ごとの Active Sensing の効果を、実機で 8 時間以上かけて比較したうえで本決定の見直しを判断する。
