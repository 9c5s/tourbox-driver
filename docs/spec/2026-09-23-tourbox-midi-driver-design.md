# TourBox Elite MIDI ドライバ設計

> レビュー状態: codex-review-loop round 6 PASS (2026-09-23)。累積 41 件 (round 1: 24、round 2: 11、round 3: 6) をすべて反映し、却下なし。実機で確認する残項目は 9 章の受け入れ確認 1 (アンロック応答の到着遅延) と 5b (5 秒未満のポート再起動)

作成日: 2026-09-23

## 1. 目的と範囲

設計上の決定の理由と却下した案は `docs/adr/` の ADR に記録する。本書は決定の内容だけを書く。

TourBox Elite (モデル名 TBECA) を、公式コンソールアプリに依存せず MIDI コントローラーとして使うためのドライバを作る。
対象 OS は Windows と macOS である。

本書の範囲は次のとおり。

- デバイスとの通信 (USB と BLE) を担うライブラリ
- ライブラリの上で動き、操作を MIDI メッセージに変換する常駐アプリ
- DAW などから受信した MIDI でハプティクス (回転操作の手応え) を切り替える機能

次のものは対象外とする。

- GUI による設定画面
- キーボードやマウス入力への変換 (公式コンソールの代替)
- TourBox Elite 以外のモデルの検証 (プロトコルは同一とされるが、本書では扱わない)
- 単発の振動 (デバイスにそのコマンドが存在しないことを 2026-09-23 の実機キャプチャで確認済み。詳細は 2.5 節)

## 2. 前提となるプロトコル

プロトコルは Linux 向けの非公式ドライバで解析済みであり、本書はその結果と実機キャプチャに基づく。
参照元は AndyCappDev/tuxbox (MIT)、rowan-mcalpin/TourBoxForLinux (MIT)、jasonrohrer/tourBoxEliteLinuxDriver (ライセンス未指定) の 3 リポジトリである。
ライセンス未指定のリポジトリは事実の確認にのみ使い、コードは流用しない。

### 2.1 接続方式

**USB** は CDC ACM (仮想シリアル) で、VID `0xC251`、PID `0x2005` である。
Windows では COM ポート、macOS では `/dev/cu.usbmodem*` として見える。
ボーレートは動作に影響しないため、115200 で開く。
DTR の要否は未確認であり、公式コンソールが DTR を立てていたことに合わせて、開くときに DTR を立てる。

**BLE** は広告名が "TourBox" で始まる。
サービス UUID は `0000fff0-0000-1000-8000-00805f9b34fb` で、通知用キャラクタリスティックが `fff1`、書き込み用が `fff2` である。
書き込みは Write Without Response を使う。
標準の BLE ペアリングは不要で、アプリケーション層のアンロックで認証する。
ファームウェアによっては初回の発見にデバイス側のペアリングモード (電源スイッチ上のボタンを 2〜3 秒長押し) が必要とされる。

USB と BLE で、アプリケーション層のメッセージは完全に同一である。
違いはトランスポートと、BLE で 20 バイトごとに分割する点だけである。

### 2.2 初期化シーケンス

1. **アンロック** の 8 バイト `55 00 07 88 94 00 1a fe` を送る。
2. 応答 (26 バイト程度) を受け取る。先頭バイトはファームウェアにより異なるため、先頭バイトに依存した判定はしない。
3. **ハプティクス設定** の 94 バイトメッセージを送る (2.4 節)。
4. 以降、デバイスから 1 バイトずつイベントが届く。

既存ドライバは、アンロックとハプティクス設定の両方を送ってからイベントを受け取っている。
アンロックだけでイベントが届くかは未確認であり、本設計は常に両方を送る。
アンロック前に何かを書き込むと、ASCII 文字列 `<!not_allow_config!>` が返る。
再接続のたびに、この初期化を最初からやり直す。

### 2.3 イベント

イベントは 1 バイトである。
下位 6 ビットがコントロール ID、bit7 が解放 (0 が押下、1 が解放)、bit6 が回転方向 (0 が CCW または下、1 が CW または上) を表す。
コントロールはボタン 14 種と回転 3 軸の計 17 種で、イベント値は押下と解放、回転の両方向を合わせて 34 値である。

| ボタン | 押下 | 解放 |
|---|---|---|
| Tall | `00` | `80` |
| Side | `01` | `81` |
| Top | `02` | `82` |
| Short | `03` | `83` |
| Scroll 押込 | `0a` | `8a` |
| 十字 上 | `10` | `90` |
| 十字 下 | `11` | `91` |
| 十字 左 | `12` | `92` |
| 十字 右 | `13` | `93` |
| C1 | `22` | `a2` |
| C2 | `23` | `a3` |
| Tour | `2a` | `aa` |
| Knob 押込 | `37` | `b7` |
| Dial 押込 | `38` | `b8` |

| 回転 | CW または上 | CCW または下 |
|---|---|---|
| Knob | `44` | `04` |
| Scroll | `49` | `09` |
| Dial | `4f` | `0f` |

回転は 1 ノッチごとに 1 バイト届き、押下と解放の対はない。
同時押しに専用コードはなく、各コントロールの押下と解放が独立に届くだけである。
tuxbox だけが「回転停止」として `84`、`89`、`8f` を定義しているが、実機での発生は未確認であり、本設計では未知の値として扱う。

### 2.4 ハプティクス設定メッセージ

94 バイト固定長で、ヘッダ `b5 00 5d` の後に (ID、値) の 2 バイト組が 45 組続き、終端が `fe` である。
ID バイトの並びは固定で、全値 0 のテンプレートは次のとおり (値バイトを `00` で示す)。

```
b5 00 5d 04 00 05 00 06 00 07 00 08 00 09 00 0b 00 0c 00 0d 00
0e 00 0f 00 26 00 27 00 28 00 29 00 3b 00 3c 00 3d 00 3e 00
3f 00 40 00 41 00 42 00 43 00 44 00 45 00 46 00 47 00 48 00
49 00 4a 00 4b 00 4c 00 4d 00 4e 00 4f 00 50 00 51 00 52 00
53 00 54 00 a8 00 a9 00 aa 00 ab 00 fe
```

値バイトは強度と速度の和で、強度は なし `0x00`、弱 `0x04`、強 `0x08`、速度は 速い `0x00`、中速 `0x01`、遅い `0x02` である。
値バイトのオフセット (0 起点) は次のとおり。

| 修飾 | Knob | Scroll | Dial |
|---|---|---|---|
| なし | 4 | 14 | 24 |
| Tall | 6 | 16 | 86 |
| Short | 8 | 18 | 88 |
| Top | 10 | 20 | 90 |
| Side | 12 | 22 | 92 |
| 十字 上 | 42 | 26 | 74 |
| 十字 下 | 44 | 28 | 76 |
| 十字 左 | 46 | 30 | 78 |
| 十字 右 | 48 | 32 | 80 |
| Knob 押込 | 34 | 56 | 68 |
| Scroll 押込 | 36 | 54 | 70 |
| Dial 押込 | 38 | 58 | 66 |
| Tour | 40 | 60 | 72 |
| C1 | 50 | 62 | 82 |
| C2 | 52 | 64 | 84 |

対象は回転 3 軸だけで、ボタンにはハプティクス設定がない。
デバイスが区別できる組み合わせは「修飾 1 つと軸」までである。
設定は起動時だけでなく随時再送でき、部分更新のコマンドはない。
94 バイトメッセージへの応答は観測されていない (2.5 節のキャプチャで、送信直後の受信は 1 バイトのイベントだけだった)。

### 2.5 実機キャプチャで確認した事実

2026-09-23 に、公式コンソール 5.11.3 (Windows) と TourBox Elite の USB 通信を USBPcap で記録した。
取得した 94 バイトメッセージ 6 件と固定テンプレートは `docs/protocol/haptic-captures.md` に保存してあり、テストの期待値として使う (8.1 節)。
確認できた事実は次のとおり。

- 「触覚: なし / 弱 / 強」「回転速度: 速い / 中速 / 遅い」「触覚フィードバック作動」の操作中、ホストが送ったメッセージは 30 件すべてが 94 バイトのハプティクス設定だった。他の種類のメッセージはなかった。
- 値の対応は 2.4 節の表と一致した。「触覚フィードバック作動」OFF は強度をすべてなしにした設定の送信で、Knob 単体、Tall+Knob、Scroll 単体の速度ビット (中速) は残っていた。
- 公式コンソールの UI は軸単位の設定だが、変更時に書き換わったのは 12 の組み合わせ (単体と、Tall、Top、Side 以外の修飾との組み合わせ) で、Tall、Top、Side との組み合わせは変わらなかった。プリセットで個別に設定されている組み合わせは除外されると推定する (UI 上では未確認)。プロトコル上は組み合わせごとに独立の値を持てる。
- 初期状態のキャプチャでも値は一様ではなく、UI の表示 (3 軸とも「強」「中速」) と一致しない組み合わせがあった。詳細は `docs/protocol/haptic-captures.md` の備考にある。
- USB と BLE が同時に接続されている状態で、公式コンソールは USB 側だけを使っていた。
- アクティブウィンドウの切り替えでプリセットが自動切替され、そのたびに 94 バイト全体が再送されていた。

### 2.6 既知の注意点

- アンロック応答 (約 26 バイト) をイベントとして解釈すると、末尾の `00` の連続が Tall 押下と誤認され、修飾が押しっぱなしになる。シリアルの読み取り境界はメッセージ境界と一致しないため、受信長で応答を判定することはできない。本設計は初期化の状態機械で「応答を受け取る期間」を区切り、その期間の受信をイベントにしない (4.3 節)。
- 未確認の項目は次のとおり。アンロックのみでイベントが届くか、26 バイト応答の各フィールドの意味、DTR の要否、回転停止イベントの実在、Elite Plus 固有の差異。

## 3. 全体構成

### 3.1 要件のまとめ

- 出力は MIDI のみとし、OS の MIDI 出力ポートを選んで送る。macOS では仮想ポートを自前で作成し、Windows では loopMIDI などが作った既存ポートを選ぶ。
- MIDI 入力ポートを持ち、受信した Control Change でハプティクスの強度と速度を切り替える。
- 操作と MIDI メッセージの対応は TOML の設定ファイルで定義し、ファイルの変更を検知して自動で再読込する。
- 回転操作は絶対値 CC と相対値 CC を操作ごとに選べる。ボタンは Note を既定とし、CC にも切り替えられる。
- 修飾ボタンを押している間だけ有効なマッピングのレイヤを持つ。
- 接続は USB と BLE の両方を初期対象とする。
- 実装言語は Rust とする。

Windows の仮想 MIDI ポートについては、teVirtualMIDI SDK の組み込みを検討したうえで採用しなかった。
同 SDK はフリーウェアではなく、配布に作者の事前許可が必要で、ドライバ本体は loopMIDI か rtpMIDI の事前インストールに依存するためである。
loopMIDI を利用者にインストールしてもらい、アプリは既存ポートを選ぶ方式にする。

### 3.2 ワークスペース

Cargo ワークスペースに 2 つのクレートを置く。

```
tourbox-driver/
  Cargo.toml                 # ワークスペース定義
  crates/tourbox/            # ライブラリ
    src/lib.rs
    src/protocol/            # ボタン、軸、イベント、メッセージの変換
    src/transport/           # Transport トレイト、usb、ble、fake (feature)
    src/device.rs            # 接続の一生の管理
    src/error.rs             # transport のエラー型
    tests/                   # 統合テスト (fake feature を使う)
  crates/tourbox-midi/       # 実行ファイル (lib + 薄い main)
    src/lib.rs               # 各モジュールの登録。テストはここから内部 API に届く
    src/main.rs              # コマンドラインの解釈と lib への委譲だけ
    src/cli.rs               # clap の定義
    src/config/              # TOML の読込と検証、解決、監視、差分
    src/engine.rs            # 修飾状態、絶対値、Event から MIDI への変換
    src/midi_msg.rs          # Note On、Note Off、CC の 3 バイト表現
    src/midi.rs              # ポートの列挙と選択、送受信
    src/output.rs            # 出力ポートの再試行状態と台帳
    src/input.rs             # 入力ポートの再試行状態
    src/haptics.rs           # 受信 MIDI からハプティクス設定への変換
    src/commands/            # run、dump、list-ports
    src/commands/reload.rs   # 設定の再読込の反映手順
  docs/protocol/haptic-captures.md   # 実機キャプチャ (テストの期待値)
  config.example.toml
  lefthook.yml
  .github/workflows/ci.yml
```

**tourbox** (ライブラリ) は MIDI を一切知らない。
**tourbox-midi** (実行ファイル) はプロトコルのバイト列を一切知らない。
この境界により、ライブラリは実機なしで単体テストでき、将来別の出力を作るときもライブラリを変更せずに済む。

テスト用のフェイク (4.2 節) はライブラリの `fake` feature で公開し、ライブラリ自身の統合テストでは dev-dependencies で自クレートを `features = ["fake"]` 付きで参照して有効にする。
この自己参照により、`cargo test` の実行時は `fake` が有効になり、`cargo build` では無効になる。
ワークスペース側の設定は加えない (ADR-0015)。

### 3.3 実行基盤と共通ライブラリ

- 非同期基盤は tokio とする。BLE ライブラリの btleplug が非同期 API だからである。
- シリアル読み取りは serialport クレートの同期 API を専用スレッドで回し、tokio の mpsc チャネルで非同期側へ渡す。
- MIDI は midir を使う。
- 設定ファイルの監視は notify と notify-debouncer-mini を使う。
- コマンドラインは clap を使う。
- ライブラリのエラー型は thiserror で定義し、実行ファイル側は anyhow で文脈を付けて集約する。
- ログは tracing を使い、`RUST_LOG` でレベルを制御する。

## 4. 通信層 (crates/tourbox)

### 4.1 protocol モジュール

純粋な変換だけを担い、I/O を持たず、エラー型も持たない。

- **Button** 列挙 (14 種) と **Axis** 列挙 (Knob、Scroll、Dial)、**Direction** 列挙 (2.3 節の表に対応)。
- **Event** 列挙: `Press(Button)`、`Release(Button)`、`Rotate(Axis, Direction)`、`Unknown(u8)`。
- `decode(u8) -> Event`: 2.3 節のビット規則で復号する。未知の値は `Unknown` として返し、上位はログのみで無視する。
- `UNLOCK`: 8 バイトの定数。
- `NOT_ALLOW_CONFIG`: ASCII 文字列 `<!not_allow_config!>` (20 バイト) の定数。
- **NotAllowConfigDetector**: 受信のかたまりをまたいで逐次照合する検出器。`feed(&[u8]) -> bool` で、これまでに与えたバイト列の末尾に文字列が完成した時点で true を返す。内部には文字列長までの一致状態だけを持ち、`reset()` で初期化する。
- **Strength** (Off、Weak、Strong) と **Speed** (Fast、Medium、Slow)、**Modifier** (なし + Button 14 種)。
- **HapticConfig**: 「軸 × 修飾」ごとに強度と速度を持つ構造体。94 バイトへの組み立てを `encode()` で行い、軸単位でまとめて設定する `set_axis(axis, strength, speed)` (公式コンソールと同じ使い勝手) と、組み合わせ単位の `set(axis, modifier, strength, speed)` を持つ。組み合わせ単位の部分更新として、強度だけを変える `set_strength(axis, modifier, strength)` と速度だけを変える `set_speed(axis, modifier, speed)` も持つ (6.2 節のハプティクス制御が使う)。

### 4.2 transport モジュール

バイト列の送受信だけを担う。

**Transport** トレイトは、送信 (`send(&[u8])`、送信完了まで待つ)、受信チャネル (バイト列のかたまりを送出する)、切断通知、停止 (`close()`、読み取りスレッドや BLE 接続の終了を待つ) の 4 つを提供する。

**usb** 実装は serialport で VID `0xC251`、PID `0x2005` のポートを自動検出する。
設定でポート名の明示指定もできる。
115200 で開き、DTR を立て、読み取りタイムアウトを 100 ms にする。
これらは serialport の `SerialPortBuilder` に渡す (DTR は `dtr_on_open(true)`。https://docs.rs/serialport/latest/serialport/struct.SerialPortBuilder.html#method.dtr_on_open)。ボーレートと DTR はイベントの受信だけでは設定漏れを検出できないため、ビルダーを組み立てる関数 `port_builder(path)` を切り出し、`UsbTransport::open` は必ずこの関数を使う。`SerialPortBuilder` には getter がなく設定メソッドだけなので、テストは `PartialEq` で期待するビルダーと比較する (8.1 節)。
読み取りは専用スレッドで行い、届いたかたまりをそのまま受信チャネルへ送出する。
serialport の `read` はデータがないときに `TimedOut` を返す (POSIX 実装は poll のタイムアウトで、Windows 実装は読み取り長 0 で、それぞれ `io::ErrorKind::TimedOut` を返す。docs.rs の `serialport/posix/poll.rs` と GitHub の `src/windows/com.rs` で確認)。
したがって `TimedOut` と `Interrupted` は切断ではなく、読み取りを続ける。
それ以外の I/O エラーとポートの消失を切断とみなす。
ポートは検出できたが他のプロセスに開かれていて開けない場合は `TransportError::Busy` にする。`Busy` は「未検出」と区別し、`Auto` でも BLE へは進まず、再接続の間隔で同じポートを再試行する (USB で同じデバイスへ複数起動した場合、後から起動した側が待ち続ける)。BLE で同じデバイスへ複数起動した場合の排他は OS と btleplug の挙動に依存し、本設計では保証しない。

**ble** 実装は btleplug で広告名 "TourBox" の前方一致をスキャンし、`fff1` の通知を購読して `fff2` に書き込む。
94 バイトは 20 バイトずつ 10 ms 間隔で分割送信し、`send` は最後の分割の書き込みが終わるまで戻らない。
この分割は ble 実装の内部に閉じ込め、上位は 94 バイトをそのまま渡す。
btleplug の切断イベントを切断とみなす。

**fake** 実装 (`fake` feature) は、送信内容の記録、受信データの注入、切断の発生、`close` の呼び出し記録をテストから操作できる。

接続設定 **ConnectionConfig** は `transport: TransportKind` (`Auto`、`Usb`、`Ble` の列挙) と `usb_port: Option<String>` を持つ。
`usb_port` は `Auto` と `Usb` で使い、`Ble` では無視する。
`Auto` は接続と再接続のたびに USB のポート検出を先に試し、見つからなければ BLE を 10 秒スキャンする。
どちらも見つからなければ device モジュールの再接続間隔で繰り返す。

### 4.3 device モジュール

接続の一生を管理する。

**公開 API**

- `Device::run(ConnectionConfig, HapticConfig) -> (DeviceEvent の受信チャネル, DeviceHandle)`。transport の生成関数を差し替えられるようにし、テストでは fake を注入する。
- **DeviceEvent**: `Input(Event)`、`Connected`、`Disconnected`。
- `DeviceHandle::set_haptics(HapticConfig)`: 更新要求を出す。すぐ戻る。
- `DeviceHandle::shutdown()` (非同期): 再接続の待機、初期化、送信のどの途中でも停止要求を出し、transport の `close` とタスクの終了を待ってから戻る。完了を保証するのはこの呼び出しだけである。ハンドルの `Drop` は停止要求を出すだけで、完了は待たない (同期の `Drop` から非同期の完了待ちはできないため)。

**初期化の状態機械**

受信長で応答を判定しない。状態で「応答を受け取る期間」を区切る。
受信は device のタスクが 1 かたまりずつ順に処理し、状態の判定はそのかたまりを処理する時点の状態で行う (チャネルに残っているかたまりは、取り出した時点の状態で扱われる)。

1. `Unlocking`: UNLOCK を送る。この状態の受信はすべて捨てる。静穏タイマーは最初の受信までは動かさず、最初の受信で 200 ms のタイマーを開始し、以後は受信のたびに 200 ms に再設定する。満了したら次へ進む。送信から 1 秒経過したら受信の有無にかかわらず打ち切って次へ進む。したがって無受信なら送信から 1 秒後に、最初の受信が遅れた場合はその受信から 200 ms 後 (ただし 1 秒を超えない) に次へ進む。無受信の場合はログに出す (アンロック応答は解析に使わない)。
2. `Configuring`: HapticConfig の 94 バイトを送り、送信完了から 200 ms 待つ。この状態の受信も捨てる。
3. `Running`: 以後の受信は 1 バイトずつ `decode` して `Input` として送出する。`Running` に入った時点で `Connected` を送出する。

この時間による区切りは保証ではない。応答の末尾が `Running` への移行より後に届けば、その `00` は Tall の押下として復号される。アンロック応答の到着遅延の実測値はまだなく、200 ms と 1 秒は初期値である。`dump` は各状態での受信バイトとその時刻をログに出し、受け入れ確認 (9 章) で応答が静穏期間内に収まることを実機で確認する。収まらない場合は静穏期間を実測に合わせて延ばす。

`Unlocking` に入るたびに NotAllowConfigDetector を `reset` し、以後の全状態で受信をすべて `feed` する。`Configuring` と `Running` で検出したら、アンロックが効いていないので `Disconnected` を送出して初期化を最初からやり直す。検出状態は状態遷移をまたいで保持するので、文字列が複数のかたまりに分かれても検出できる。

**ハプティクス更新**

- `set_haptics` は最新値を保持し、送信は 1 つのタスクが直列に行う。送信中に届いた更新は最新値だけを保持する。
- 送信完了から次の送信開始までは 50 ms 以上あける。待機中 (送信中でも初期化中でも切断中でもない) に届いた更新は、直前の送信完了から 50 ms 経過した時点か、経過済みなら即時に送信を開始する。送信中に届いた更新は、その送信の完了から 50 ms 後に開始する。つまり更新から送信開始までの遅延は、待機中なら最大 50 ms、送信中なら「残りの送信時間 + 50 ms」であり、送信自体にかかる時間 (BLE の分割送信では 40 ms 以上) は含まない。
- 直前に送った内容と同じ値は送らない (べき等)。
- 初期化中と切断中の更新は最新値を保持する。切断中に届いたものは再接続の初期化 (`Configuring`) で送り、初期化中に届いたものは初期化完了後の待機で送る。

**切断と再接続**

- 切断を検知したら `Disconnected` を送出し、1 秒から 2 倍ずつ最大 30 秒の間隔で再接続する。再接続時は初期化を最初からやり直し、直前の HapticConfig を送る。
- スリープからの復帰は、OS からの切断通知 (USB ポートの消失、BLE の切断) で検知し、通常の再接続に任せる。切断通知が来ない環境がないかは受け入れ確認で見る (9 章)。

修飾ボタンの押下状態はライブラリでは持たない。
ライブラリは生の Press と Release を送出し、修飾の解釈は実行ファイル側の engine の責務とする。

**macOS の BLE 権限**

btleplug の README によると、macOS 11 以降で BLE を使うには、アプリバンドルの Info.plist に `NSBluetoothAlwaysUsageDescription` を入れるか、コマンドラインアプリではそれを起動するターミナルアプリに「システム設定 > プライバシーとセキュリティ > Bluetooth」で権限を与える必要がある (https://github.com/deviceplug/btleplug#macos)。
この設定画面の名称は macOS 13 以降のものであり、macOS 11 と 12 では「システム環境設定 > セキュリティとプライバシー > プライバシー > Bluetooth」である。
本アプリはコマンドラインで配布するため、ターミナルアプリへの権限付与の手順を README に書き、権限がない場合は ble 接続を失敗として扱ってログに案内を出す。

## 5. マッピングと設定ファイル (crates/tourbox-midi)

### 5.1 ファイルの場所と読込

設定は TOML の 1 ファイルである。
パスは `--config` で指定し、省略時は OS の設定ディレクトリ (Windows は `%APPDATA%\tourbox-midi\config.toml`、macOS は `~/Library/Application Support/tourbox-midi/config.toml`) を使う。
リポジトリに `config.example.toml` を同梱する。

起動時に読み込み、構文エラーと検証エラーは行番号付きのエラーで即終了する。
`[map]` と `[midi]` は必須とし、空ファイルは必須セクションの欠落として検証エラーになる。

### 5.2 構造

```toml
[device]
transport = "auto"   # auto | usb | ble
# usb_port = "COM3"  # auto と usb で使う明示指定。ble では無視

[midi]
output = "TourBox MIDI"      # macOS は仮想ポートをこの名前で作成、Windows は既存ポート名の部分一致で選択
input = "TourBox MIDI In"    # ハプティクス制御の受信用。省略可
channel = 1                  # 既定チャンネル (1〜16)

[haptics]
knob = { strength = "strong", speed = "medium" }
scroll = { strength = "weak", speed = "fast" }
dial = { strength = "off" }
[haptics.with.side]          # 修飾と軸の組み合わせの上書き (省略時は軸の値を継承)
knob = { strength = "weak" }

[haptics.control]            # 受信 MIDI によるハプティクス制御 (6.2 節)
channel = 16
master = { cc = 99 }
knob = { cc = 100 }
scroll = { cc = 101, speed_cc = 102 }
[haptics.control.with.side]
knob = { cc = 110 }

[map]
tall = { note = 60 }                    # ボタン: Note On (押下) と Note Off (解放)。velocity 省略時 127
top = { cc = 20 }                       # ボタンを CC にする場合: 押下 127、解放 0
c1 = { note = 62, channel = 2 }         # チャンネルは項目ごとに上書き可
knob = { cc = 1 }                       # 回転: 絶対 CC (既定)。内部値 0〜127、1 ノッチ 1 ずつ
scroll = { cc = 2, mode = "relative" }  # 相対 CC。encoding は twos_complement (既定) か binary_offset
dial = { cc = 3, step = 2, invert = true }
knob_press = { note = 64 }              # 押込はボタンと同じ扱い (scroll_press、dial_press も同様)
up = { note = 65 }                      # 十字キーは up、down、left、right
[map.with.side]                         # Side を押している間だけ有効なレイヤ
knob = { cc = 11 }
top = { note = 70 }
```

`[haptics]` の各軸は `strength` (`off`、`weak`、`strong`。既定 `strong`) と `speed` (`fast`、`medium`、`slow`。既定 `medium`) を持つ。
既定値は公式コンソールの UI 表示 (「強」「中速」) に合わせて選んだ本ドライバの値であり、取得した初期状態のペイロード (2.5 節、組み合わせによって速度が異なる) とは同一ではない。

回転操作の項目は次のキーを持つ。

- `cc`: CC 番号 (0〜127)。
- `mode`: `absolute` (既定) か `relative`。
- `encoding` (relative のみ): `twos_complement` (既定。+1 は 1、-1 は 127) か `binary_offset` (+1 は 65、-1 は 63)。
- `step`: 1 ノッチあたりの増減量。絶対は 1〜127、相対は 1〜63 (7 ビットの 2 の補数では +64 と -64 が同じ値になり、binary_offset では 64 を超えると 7 ビットに収まらないため)。既定 1。
- `initial` (absolute のみ): 内部値の初期値 (既定 0)。
- `invert`: 回転方向を反転する (既定 false)。
- `channel`: チャンネルの上書き。

ボタンの項目は `note` か `cc` のどちらか一方を持ち、`channel` を上書きできる。`velocity` は `note` の項目だけで上書きできる。

**検証と解決**

- 範囲外の値、未知のキー、存在しないコントロール名、`note` と `cc` の両方指定、`step` の範囲外、`[haptics.control]` 内で同じ (チャンネル、CC 番号) を複数項目に割り当てた場合はエラーにする。
- 検証に通った設定は `Config::resolve_mapping()` で **MappingSet** に解決する。`[haptics.control]` は **HapticsControlConfig** として取り出す。MappingSet は「レイヤ (なし + 修飾ボタン) × 操作」ごとの割り当てで、チャンネルは `midi.channel` と項目の `channel` を解決済みの値として持つ。engine は MappingSet だけを受け取り、`midi.channel` を知らない。

### 5.3 修飾ボタンとメッセージの規則

- `[map.with.<ボタン>]` が定義されたボタンを**修飾ボタン**と呼ぶ。
- 修飾ボタンを押している間、そのレイヤに定義がある操作はレイヤの割り当てを使い、定義がない操作は通常の割り当て (基本レイヤ) を使う。基本レイヤにフォールバックした絶対 CC は基本レイヤの内部値を使う。
- 同時に有効な修飾は 1 つ (先に押した方) である。修飾中に別の修飾ボタンを押した場合は、現在のレイヤでの通常ボタンとして扱う。先の修飾を離しても、押したままの後のボタンは修飾に昇格しない (基本レイヤに戻る)。
- 修飾ボタン自身の `note` や `cc` は通常どおり送る (押下で On、解放で Off)。送りたくなければその項目を書かない。
- 絶対 CC の内部値は「レイヤ × 操作」ごとに独立に保持する。
- **押下と解放の対応**: ボタンの押下時に送ったメッセージの種類 (Note か CC)、番号、チャンネルを engine が記憶し、解放時はその記憶に対応する Note Off または CC 0 を送る。解放時に割り当てを引き直さない。これにより、修飾レイヤの切替中に押下と解放で割り当てが変わっても Note On が残らない。
- engine が返すのは **Outgoing** (MIDI メッセージと由来の組) である。由来は `ButtonOn`、`ButtonOff`、`Rotation` の 3 種で、出力層の台帳 (6.1 節) はボタン由来だけを扱う。回転による CC (絶対値 127 や相対値の -1 を表す 127 を含む) は台帳に入らない。
- `release_all()` は記憶している押下中のボタンすべてに対応する Off (由来 `ButtonOff`) を返し、修飾状態と押下状態を初期化する。デバイスの `Disconnected`、アプリの終了、設定の再読込で使う。
- engine が返す Off が実際に届いたかは engine では分からない。送信の成否に基づく回収は出力層の台帳 (6.1 節) が担う。

### 5.4 自動再読込

- notify で設定ファイルの**親ディレクトリ**を監視し、対象ファイル名のイベントだけを扱う。エディタによってはファイルを置換して保存するため、ファイル単体の監視では置換後を追えない (notify のドキュメント「Editor Behaviour」による。https://docs.rs/notify/latest/notify/)。
- notify-debouncer-mini で 300 ms のデバウンスをかける。これは連続イベントをまとめる目安であり、保存完了の保証ではない。
- 変更検知後は読込と検証を先に行い、構文エラーか検証エラーなら内容をログに出して現在の設定を維持する。起動時と違い、終了はしない。保証はここまでで、途中まで書かれた内容でも検証に通れば反映される (その後の保存でもう一度再読込が走る)。ファイルを置換して保存するエディタなら途中の内容は読まれない。
- 検証に通ったら次の順で反映する。
  1. engine の `release_all()` の結果を出力層に渡し、修飾状態と押下状態を初期化する。出力層は台帳 (6.1 節) に従って Off を送る。
  2. `map` と `midi.channel` から解決した MappingSet を engine の `replace_mapping()` に渡す。絶対 CC の内部値は、同じ「レイヤ × 操作」に同じ `cc`、`mode`、`encoding` の割り当てが残っていれば引き継ぎ、それ以外は `initial` に戻す。
  3. ハプティクス制御 (6.2 節) の `reset()` に新しい HapticsControlConfig と基準値 (`[haptics]` から作った HapticConfig) を渡して作り直し、実行中の上書きを捨て、返ってきた基準値を device の `set_haptics` に渡す。device 側のべき等性により、直前に送った値と同じなら送信は起きない。
  4. `midi` セクションの `output` か `input` に差分があれば該当ポートを開き直す。差分がなくても、Windows の入力ポートは再読込のたびに閉じて開き直す (6.2 節の復旧手順のため)。出力を開き直す前に、台帳にある On の Off を古いポートへ送ってから (失敗しても続行) 台帳を空にする。
  5. `device` セクションに差分があれば `shutdown()` の完了を待ってから新しい設定で `Device::run` する。
- 反映結果はログに出す。

### 5.5 engine の責務

engine は、修飾状態の管理、押下中のボタンの記憶、絶対値の保持、Event から MIDI メッセージ列への変換を担う。
公開 API は `Engine::new(MappingSet)`、`handle(DeviceEvent) -> Vec<Outgoing>` (`Disconnected` では `release_all()` と同じ結果を返す)、`release_all() -> Vec<Outgoing>`、`replace_mapping(MappingSet)` の 4 つである。
engine は出力ポートの状態を知らない。出力が待機中でも run は DeviceEvent を engine に渡し続け、押下、解放、回転、切断による状態更新は途切れない。捨てられるのは engine が返した Outgoing のうち送信できなかったものだけである (6.1 節)。
純粋な関数と小さな状態機械で書き、実機なしで単体テストする。

## 6. MIDI 入出力とハプティクス制御

### 6.1 MIDI 出力

出力ポートの扱いは OS で分ける。

- macOS では設定の `output` 名で仮想ポートを作成する。CoreMIDI では自作の仮想出力は Source として登録され、他のアプリの入力一覧に現れる。自分の出力一覧 (`MidiOutput::ports()` が返す Destination) には現れないので、一覧による消失監視は行わない (midir の CoreMIDI 実装 https://github.com/Boddlnagg/midir/blob/master/src/backend/coremidi/mod.rs で確認)。作成に失敗したら 5 秒ごとに再試行し、送信エラーが起きたら閉じて作り直す。
- Windows では既存の出力ポートを `output` 名で選ぶ (`port_candidates`)。完全一致を優先し、次に部分一致、複数あればログに候補を出して先頭を使う。見つからなければ候補一覧をログに出し、5 秒ごとに再試行する。loopMIDI を後から起動した場合に備えるためである。接続中も 5 秒ごとに一覧を再評価し、選んだポート名がなくなっていたら閉じて再試行状態に戻る。
- 出力ポートの待機中も、設定ファイルの監視と Ctrl+C の受付は動く。誤ったポート名を設定ファイルで直せば、再読込で待機から抜ける。待機中も DeviceEvent は engine に渡して状態を更新し、engine が返した Outgoing だけを捨てる (溜めない)。絶対 CC の内部値は待機中の回転でも進むため、復帰後の DAW の値と一致しないことがある。
- 送るのは Note On、Note Off、Control Change の 3 バイトメッセージのみとし、ランニングステータスは使わない。
- 出力層は**台帳**を持つ。由来が `ButtonOn` の送信に成功したら (チャンネル、種類、番号) を台帳に入れ、由来が `ButtonOff` の送信に成功したら台帳から消す。`ButtonOff` の送信に失敗した場合は台帳に残る。由来が `Rotation` のメッセージは台帳を変更しない。
- 送信エラー (loopMIDI の終了など) はログに出し、ポートを閉じて再選択の再試行に戻る。復帰時は台帳にある On すべてに対応する Off を新しいポートへ送り、成功したものを台帳から消す。engine の押下状態は物理ボタンの状態として維持し、復帰のために初期化しない。
- `list-ports` サブコマンドで入出力ポートの一覧を表示する。設定に書く名前の確認用である。

### 6.2 MIDI 入力によるハプティクス制御

- 設定の `input` 名で、macOS は仮想ポートを作成し、Windows は既存の入力ポートを選ぶ。選び方は出力と同じで、出力とは独立した状態として扱う (出力が待機中でも入力は動き、その逆も同じ)。`input` が未設定なら入力機能は無効である。
- macOS の自作仮想入力は Destination として登録され、自分の入力一覧 (`MidiInput::ports()` が返す Source) には現れないので、出力と同じく一覧による消失監視は行わず、作成失敗時の 5 秒ごとの再試行だけを行う。
- Windows では、midir の入力接続に切断通知がなく、受信がないことと消失を区別できない。そのため 5 秒ごとにポート一覧を再評価し、選んだポート名がなくなっていたら接続を閉じて再試行状態に戻り、再び現れたら開き直す。
- この方式で自動復帰を保証するのは、一覧の再評価で消失を 1 度でも観測できた場合に限る。5 秒未満で同名のポートが消えて再び現れた場合 (loopMIDI の短時間の再起動など) は消失を観測できず、旧接続が無効なまま残る可能性がある。この場合の復旧手順は、設定ファイルを保存し直して再読込を起こす (5.4 節の手順 4 で入力ポートを開き直す) か、アプリを再起動することとし、README に書く。5 秒未満の再起動で旧接続がどうなるかは受け入れ確認 (9 章) で実機確認する。
- 受信側で `parse_control_change` により Control Change だけを取り出し、他のメッセージは捨てる。
- 制御の本体は **HapticsController** で、`new(HapticsControlConfig, 基準の HapticConfig)`、`on_cc(channel, cc, value) -> Option<HapticConfig>`、`reset(HapticsControlConfig, 基準の HapticConfig) -> HapticConfig` を持つ。
- `[haptics.control]` の各項目は次の意味を持つ。
  - `channel`: 受信するチャンネル。省略時は全チャンネル。
  - `master = { cc = N }`: 値 0〜63 で全軸をなし、64〜127 で設定値に戻す (公式コンソールの「作動」スイッチ相当)。なしの間は強度も速度も 0 にした 94 バイトを送る。なしの間に届いた軸ごとの変更は保持しておき、master が戻ったときに反映する。
  - `<軸> = { cc = N, speed_cc = M }`: `cc` の値が 0 でなし、1〜63 で弱、64〜127 で強。`speed_cc` の値が 0〜42 で速い、43〜85 で中速、86〜127 で遅い。軸への変更は、その軸の全組み合わせ (修飾なしと修飾付き) に適用する。ただし `[haptics.control.with.<修飾>]` に同じ軸の項目がある組み合わせは除外し、その項目の CC だけで制御する。
  - `[haptics.control.with.<修飾>]`: 修飾と軸の組み合わせを個別に制御する。
- 受信した変更は実行中の値にだけ反映し、設定ファイルには書き戻さない。設定ファイルの再読込があった時点で、制御の割り当てと基準値をファイルの値に作り直し、実行中の上書きは捨てる (5.4 節)。
- 変更のたびに `DeviceHandle::set_haptics` を呼ぶ。連続した変更のまとめ送信とべき等性は device 側で行う。

### 6.3 スレッドと起動順

- midir の受信コールバックは専用スレッドで動くため、tokio の mpsc チャネルへ渡してハプティクス制御タスクで処理する。
- 起動順は、設定読込、ログの初期化、Ctrl+C の受付、設定ファイル監視の開始、MIDI 出力の準備 (再試行状態)、デバイス接続の開始、MIDI 入力の準備 (再試行状態) である。
- 終了は Ctrl+C で行い、engine の `release_all()` の結果を出力層に渡し、台帳に残った On の Off も送ってから MIDI ポートを閉じ、device の `shutdown()` を待つ。

### 6.4 コマンドライン

- `tourbox-midi [--config <path>] [--verbose]`: 常駐する。
- `tourbox-midi list-ports`: MIDI の入出力ポートを一覧表示する。
- `tourbox-midi dump [--transport <auto|usb|ble>] [--usb-port <name>]`: 設定ファイルを読まず、引数の接続設定と既定の HapticConfig でデバイスに接続し、DeviceEvent を表示する。MIDI は送らない。動作確認用である。

## 7. エラー処理とログ

- 起動時に終了する致命エラーは、設定ファイルの構文エラーや検証エラー (終了コード 1、原因を行番号付きで表示) と、不正なコマンドライン引数 (clap の既定に従い終了コード 2。ヘルプとバージョン表示は 0。https://docs.rs/clap/latest/clap/error/struct.Error.html#method.exit_code) である。
- 継続して再試行する回復可能エラーは、デバイス未検出や切断、MIDI ポート未検出や送信失敗、再読込時の設定エラーである。いずれもログに出し、4 章と 6 章で定めた間隔で再試行する。
- ライブラリ側のエラー型は thiserror でモジュールごとに定義する (transport は I/O、BLE、未検出、使用中)。device はエラー型を持たず、初期化失敗と切断はログと `Disconnected` で表す。protocol はエラー型を持たない。実行ファイル側は anyhow で文脈を付けて集約する。
- 黙って捨てない。ポート未接続で捨てたイベントは debug ログに、状態の変化 (接続、切断、ポート消失、復帰、再読込) は info または warn ログに必ず出す。
- ログは tracing で、`RUST_LOG` で制御し、既定は info である。`--verbose` で受信バイトと送信 MIDI をすべて表示する。

## 8. テストと CI

テストは、合格することではなく要件を満たすことを目的にする。

### 8.1 単体テストと統合テスト

- protocol: 17 コントロールの 34 値と未知値の表駆動テスト。`UNLOCK` の値。NotAllowConfigDetector は、全 19 通りの分割位置、1 バイトずつの到着、前後に無関係なバイトが付く場合、`reset` 後に一致状態が消えることを確認する。`encode` は `docs/protocol/haptic-captures.md` の固定テンプレートと 6 件のキャプチャを期待値にする。加えて、組み合わせ単位の `set` で 1 か所だけ変えた設定を組み立て、2.4 節のオフセット表の位置だけが変わることを全 45 組で確認する (全修飾が同値のキャプチャでは検出できないオフセットの入れ違いを防ぐ)。`set_axis` が対象軸の全組み合わせを書き換えることも確認する。
- transport: fake の振る舞い自体をテストする。usb と ble の実装は自動テストの対象外とし、`dump` サブコマンドで手動確認する。ble の 20 バイト分割と 10 ms 間隔は純粋関数として切り出してテストする。usb の候補ポート絞り込み (VID/PID) も列挙結果の型を入力にしてテストする。usb がポートを開くときの設定は、`port_builder(path)` の戻り値を、テスト側で `serialport::new(path, 115200)` に `timeout(100 ms)` と `dtr_on_open(true)` を付けて組み立てた期待値と `PartialEq` で比較してテストする (期待値の組み立てに `port_builder` は使わない)。
- device: fake を使って、初期化の状態機械 (送信順序、`Unlocking` と `Configuring` の受信を捨てる、静穏タイマーが受信のたびに再設定される、1 秒の打ち切り境界、`Connected` の送出タイミング)、`Running` での 1 バイト復号 (20 バイト以上のかたまりも全件)、`NOT_ALLOW_CONFIG` が `Configuring` と `Running` をまたいで分割到着した場合の再初期化、`set_haptics` の契約 (送信完了から 50 ms の間隔、送信中の更新は完了後に最新値だけ、べき等、初期化中と切断中の保持。送信に時間のかかる fake を使う)、再接続の間隔、`shutdown` が再接続待機中、初期化中、送信中のいずれからでも `close` を呼んでタスクを終える、を tokio の時間を止めて検証する。
- engine: 修飾レイヤの切替とフォールバック、昇格しないこと、絶対 CC の 0〜127 への丸めと `step` と `initial` と `invert`、相対 CC の 2 方式の符号化と両方向、押下と解放の対応、Outgoing の由来 (ボタンの Note と CC は `ButtonOn` と `ButtonOff`、回転は `Rotation`)、`release_all` の内容、MappingSet 差し替え時の内部値の引き継ぎ条件を表駆動で確認する。
- config: `config.example.toml` が読み込めること、5.2 節の検証項目がそれぞれ行番号付きのエラーになること、空ファイルが必須セクション欠落のエラーになること、既定値と修飾ごとの上書きが HapticConfig に反映されること、MappingSet のチャンネル解決、`default_config_path()` の OS 別の値、差分検出 (5.4 節の各セクション)。
- midi: ポート名の選択ロジックと、受信バイト列から Control Change だけを取り出す関数を単体テストする。出力層は、ポートの開閉と送信と一覧取得を差し替えられる形にして、台帳の更新 (`ButtonOn` の成功で追加、`ButtonOff` の成功で削除、`ButtonOff` の失敗で残る、`Rotation` は変更しない。絶対値 127 と相対値の 127 が台帳に入らないことを含む)、復帰時の Off 送信、待機中も engine の状態更新が続くこと (待機中の修飾解放が復帰後に反映される)、Windows 方式での 5 秒ごとの再評価による消失と再出現の検知、macOS 方式では一覧に自分のポートがなくても閉じないことと作成失敗時の再試行、を検証する。入力層も同じ形で両方式を検証する。実ポートの開閉は手動確認とする。
- haptics: 6.2 節の規則 (チャンネル、値域、軸と組み合わせの適用範囲、master の保持と復帰、再読込時の作り直し) を表駆動で確認する。

### 8.2 CI とローカルのチェック

- GitHub Actions で windows-latest と macos-latest の両方で `cargo fmt --check`、`cargo build`、`cargo clippy --all-targets -- -D warnings`、`cargo test`、`cargo lint-adr` の 5 つを実行する。`cargo build` は `fake` feature を含まない出荷構成のコンパイル検査であり (ADR-0015)、`cargo lint-adr` は ADR の形式検査である (ADR-0012)。
- lefthook をリポジトリに置き、pre-commit で CI と同じ 5 つを実行する。commit-msg で Conventional Commits の形式 (`type: 要約`) を正規表現で検査する。Node などの追加依存は入れない。
- lefthook は crates.io にないため、Windows は `winget install evilmartians.lefthook`、macOS は `brew install lefthook` で入れる。README に手順とバージョンを書き、clone 後に `lefthook install` を 1 回実行する。
- pre-commit の所要時間が問題になったら、build と test を pre-push に移す (ADR-0015)。

## 9. 手動の受け入れ確認

README に次の手順を書き、リリース前に確認する。
各項目に適用 OS を付け、実機や該当 OS がなくて実施できなかった項目は「未実施」と理由を記録する (実施済みと区別する)。

1. (両 OS) USB 接続で `dump` が全コントロールのイベントを表示し、ケーブルを抜くと Disconnected、挿すと Connected が出る。`dump` のログで、アンロック応答が `Unlocking` の静穏期間内に収まっていることを確認する (収まらなければ 4.3 節の初期値を見直す)。
2. (両 OS) BLE 接続で同じことができる。macOS はターミナルへの Bluetooth 権限付与の手順を含む。
3. (両 OS) DAW が設定どおりの Note と CC を受信する (絶対 CC と相対 CC の両方)。
4. (両 OS) 修飾ボタンを押している間だけレイヤの割り当てに切り替わり、押下中にレイヤが変わっても Note On が残らない。
5. (Windows) loopMIDI を終了して 10 秒以上待ってから再起動すると、送信と受信が自動で復帰する。
5b. (Windows) loopMIDI を終了して 5 秒未満で再起動した場合の挙動を記録する。自動で復帰しなければ、設定ファイルの保存し直しで復帰することを確認する (6.2 節の制限の実機確認)。
6. (両 OS) 設定ファイルを編集すると、再起動なしで反映される。誤った編集では前の設定が維持され、ログに理由が出る。
7. (両 OS) DAW から `[haptics.control]` の CC を送ると、回転操作の手応えが変わる。
8. (両 OS、USB 接続のみ) 2 つ目のインスタンスを起動すると、ポート使用中として待機し続け (BLE へ進まない)、1 つ目を終了すると接続する。BLE 接続での複数起動は保証しないので確認対象外とする。
9. (両 OS) スリープから復帰した後に、操作なしで再接続する。

## 10. 将来の拡張

本書の範囲外だが、設計上は次の拡張を妨げない。

- Windows MIDI Services (Windows 11) を使った外部ツール不要の仮想ポート。ポート選択の抽象の裏側を差し替えるだけで済む。
- キーボード入力など別の出力。ライブラリはそのまま使える。
- Elite Plus など他モデルの対応。プロトコルは同一とされるため、VID と PID と広告名の追加が中心になる。
